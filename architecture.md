# QueueLess – Architecture

## Implemented Architecture
QueueLess uses a Next.js application backed by Supabase:

```text
Browser
   ↓ Server-rendered pages, client actions, and route handlers
Next.js application
   ↓ Supabase SSR/API client
Supabase Auth + PostgreSQL + Realtime
```

## Components
### Frontend
Responsible for:
- Public queue pages
- Owner/staff dashboards
- Forms and validation
- Real-time event display
- QR presentation

### Next.js application
Responsible for:
- Authentication
- Authorization
- Business and queue management
- Queue ordering and state transitions
- Wait-time calculation
- Analytics queries
- QR URL generation
- Route handlers for mutations

### Supabase
Stores:
- Users
- Businesses
- Staff assignments
- Queues
- Queue entries/tickets
- Status history
- Settings
- Analytics source data

## Multi-Tenant Concept
Every business-specific record must be linked to a `business_id` directly or through a related entity. Backend authorization must verify business ownership/assignment before allowing staff or owners to read or modify the record.

## Real-Time Architecture
When staff performs an action:

```text
Staff Dashboard
   ↓ POST /api/tickets/{id}/status
Database validates role + transition
   ↓
Supabase Realtime emits a Postgres change
   ↓
Staff/customer pages refresh server data
```

## Queue Ordering
A queue should use server-side ordering. The client must not be trusted to decide who is next.

Recommended ordering key:
`joined_at` plus a unique sequence/token generated by the server.

## Wait Time
For MVP:
`estimated_wait = eligible_customers_ahead × configured_average_service_minutes`

Use a more detailed calculation later only if it is needed.
